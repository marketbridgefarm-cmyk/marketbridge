# MarketBridge Security Notes — Corrected Build

## Immediate actions before deployment

1. **Rotate every credential that was present in any previous archive**, especially the database password and JWT secret. They must be considered compromised.
2. Never commit `.env`. Use `backend/.env.example` and inject production secrets through the deployment platform.
3. Set a strong random `JWT_SECRET` and `PAYMENT_WEBHOOK_SECRET` (32+ characters; 64+ is recommended).
4. Set `NODE_ENV=production` and an explicit comma-separated `CLIENT_URL` allow-list.

## Authorization fixes

- Marketplace messages require an order relationship and both sender/receiver must be participants.
- Order conversations include the assigned transport truck owner.
- Advertisers must have the `ADVERTISER` role.
- Advertisers can only attach their own listing.
- Advertisement dates are validated and expired ads cannot be activated.
- Payment creation is scoped to the authenticated buyer/participant and resource being paid for.
- Digital product purchases cannot be created for the seller's own product.
- Digital downloads require a completed purchase and a `PAID` payment.
- Rating uniqueness is enforced at both application and database level.
- Rating averages use a database aggregate rather than loading all ratings into application memory.

## Payment model

A payment row means **payment intent**, not proof of payment.

The corrected API includes a signed generic webhook endpoint. Provider integrations must translate the provider's verified event into:

```json
{
  "paymentId": "...",
  "status": "PAID",
  "reference": "...",
  "provider": "telebirr",
  "providerTransactionId": "..."
}
```

The webhook must send `X-MarketBridge-Signature`, an HMAC-SHA256 signature of the exact raw JSON request body using `PAYMENT_WEBHOOK_SECRET`.

For a real Telebirr/CBE deployment, implement provider-specific adapters and verify the provider's own webhook signature/authentication before calling the internal payment service.

The admin manual confirmation endpoint is retained only as a controlled reconciliation fallback.

## Digital products

Digital purchases are now represented by `DigitalPurchase`. Access is granted only after the linked payment becomes `PAID`.

The current download endpoint redirects to the stored `fileUrl` after authorization. **For production, do not use publicly readable file URLs.** Store files in private object storage and replace the redirect with a short-lived signed download URL generated by the storage provider.

## Testing

Run:

```bash
cd backend
npm test
```

The included tests cover core participant authorization. Add provider-specific integration tests and database-backed API tests before handling real money.
